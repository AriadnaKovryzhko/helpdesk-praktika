# Спецификация сервиса Help Desk

## Роли

Проверка ролей выполняется на сервере (RBAC).

| Код | Название | Назначение |
| --- | --- | --- |
| USER | Пользователь | Создаёт заявки и следит за своими заявками |
| AGENT | Исполнитель | Берёт заявки в работу и решает их |
| MANAGER | Руководитель | Распределяет заявки, управляет пользователями и справочниками, видит дашборд и журнал аудита |

## Модель данных

Таблицы приведены к 3НФ, используются связи 1:N и M:N, поля поиска проиндексированы:
`users`, `roles`, `user_roles` (M:N), `refresh_tokens`, `password_reset_tokens`, `categories`, `sla_policies`, `tickets`, `ticket_comments`, `ticket_attachments`, `ticket_status_history`, `notifications`, `audit_logs`.

Таблица `sla_policies` задаёт для приоритета количество минут на реакцию и решение.

## Статусы заявки

Разрешённые переходы проверяются в сервисе. Каждый переход записывается в `ticket_status_history`.

```
NEW -> ASSIGNED -> IN_PROGRESS -> WAITING_USER -> IN_PROGRESS
IN_PROGRESS -> RESOLVED -> CLOSED
RESOLVED -> IN_PROGRESS (переоткрытие)
```

## SLA

При создании заявки сроки рассчитываются по `sla_policies`. Фоновая задача раз в минуту отмечает просроченные заявки и создаёт уведомления. На клиенте идёт обратный отсчёт.

## Обязательный функционал

- Регистрация, вход по email и паролю, JWT access (15 минут) и refresh (httpOnly cookie, ротация), выход, восстановление пароля (ссылка выводится в лог).
- CRUD заявок, категорий, SLA-политик и комментариев, удаление с подтверждением.
- Списки заявок и пользователей: пагинация, поиск, сортировка и фильтры на сервере.
- Валидация на клиенте и сервере с понятными сообщениями на русском языке.
- Вложения к заявке: jpg, png, pdf, docx, до 5 МБ, проверка типа по содержимому, скачивание только через проверку прав.
- Личный кабинет: профиль, смена пароля, история заявок.
- Панель руководителя: пользователи, роли, блокировка. Заблокированный пользователь не может войти, его токены отзываются.
- Дашборд: графики по статусам, просрочкам SLA, нагрузке на исполнителей.
- Адаптив 360–1920 px, единый UI-kit, состояния загрузки, пустых списков и ошибок.

## Дополнительный функционал

1. Уведомления в реальном времени через WebSocket с авторизацией по токену.
2. Журнал аудита действий с просмотром у руководителя.

## Безопасность

- Хэширование паролей алгоритмом argon2.
- Только ORM и параметризованные запросы.
- CORS на домен клиента из переменной окружения.
- Проверка доступа к каждому ресурсу на сервере: USER видит только свои заявки, подстановка чужого идентификатора даёт 403 или 404.
- Защита от XSS.

## Архитектура

Слои: контроллеры, сервисы, репозитории. Бизнес-логика находится только в сервисах.

Единый формат ответа: `{ "data": ..., "meta": ... }`. Единый формат ошибки: `{ "error": { "code", "message", "details" } }`. Используются корректные HTTP-коды.

Swagger UI доступен на `/api/docs`. Все изменения схемы выполняются только миграциями. Seed содержит данные для всех ролей. Типовые запросы выполняются быстрее 500 мс на данных seed.

## Тесты

- Unit-тесты сервисов с покрытием сервисного слоя не менее 60%.
- Не менее 5 интеграционных тестов API с тестовой базой данных.
- Не менее 3 тестов компонентов (Vitest и Testing Library).
- 1–2 e2e-сценария на Playwright: создание заявки, уведомление исполнителю, смена статуса.

## Процесс

Ветка `main` защищена, работа ведётся в feature-ветках, сообщения коммитов следуют Conventional Commits, слияние выполняется через PR с ревью второй участницы.

## Уточнения реализации

- Исполнитель видит заявки без исполнителя и заявки, назначенные на него. Руководитель видит все заявки. Пользователь видит только свои заявки.
- Реакцией считается назначение исполнителя. Решением считается перевод заявки в статус RESOLVED. Срок SLA на время ожидания ответа пользователя не приостанавливается.
- Недоступная заявка возвращает 404, чтобы не раскрывать факт её существования.
- Создавать заявки может только роль USER, обрабатывают заявки только AGENT и MANAGER. Роль USER не совмещается с ролями сотрудников. Автор заявки не может её взять, получить в назначение или вести как ответственный.
